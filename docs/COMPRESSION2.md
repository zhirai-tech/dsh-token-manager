# Compression 2.0（工具感知压缩）· 准确率优先版

> 目标：在**不影响模型准确率、不让模型遗忘上下文**的前提下，尽可能提高工具输出压缩率。
> 硬约束（用户明确要求）：
> 1. 不修改历史前缀、不重写会话、不做 KV Cache 前缀重写；
> 2. 错误结果不压缩；
> 3. 代码/文件读取结果不压缩；
> 4. 任何压缩都可逆（`token_manager_read` 恢复原文）。

## 1. 新增了什么

| 能力 | 说明 |
|---|---|
| 工具感知分类 | shell 输出自动识别为 `file-list` / `json` / `jsonl` / `markdown` / `git-diff` / `git-log` / `build-log` / `test-output` / `diff` / `log` / `text` |
| 分类摘要器 | 文件列表保留条数与首尾条目；JSON 保留顶层键/数组长度/样例；Markdown 保留全部标题与首段；git diff 保留变更文件与 +/- 统计；构建/测试保留错误、警告、汇总行 |
| 错误行全类型保留 | 无论哪种输出类型，**所有 error/warning 行（带原始行号）都会进入摘要** |
| 压缩率护栏 | 摘要若不小于原文 70%，直接放弃压缩、保留原文 |
| 精度护栏（新增） | `read` / `read_file` / `read_multiple_files` 结果**永不压缩**；`error` 结果**永不压缩**；`token_manager_read` 等工具沿用原有黑名单 |

## 3. 真实 A/B：准确性核对（同一命令、同一问题）

任务：执行 1500 行 pwsh 输出，其中第 777 行是 ERROR、第 999 行是 WARNING；然后回答总行数、第 777 行原文、ERROR/WARNING 行数。

| 组 | 压缩 | 调用数 | Token 合计 | 模型回答 |
|---|---|---|---|---|
| A | 开（on） | 3 | 47,127 | 1500 行；第 777 行原文正确；ERROR 1 / WARNING 1 |
| B | 关（observe） | 2 | 40,076 | 1500 行；第 777 行原文正确；ERROR 1 / WARNING 1 |

**准确率结论：两组事实完全一致，均正确。**

**Token 结论（重要且诚实）**：这一轮里压缩组反而多花 token（47,127 vs 40,076）。原因是模型看到"输出被压缩"后，为核对第 777 行原文主动调用了两次 `token_manager_read` 把原文读了回来——这正说明"可逆恢复"通道有效，但也说明**当任务要求逐行核对时，压缩不一定省钱**。

对照另一组"只要求结论、不需要逐行原文"的 A/B（64KB 输出、模型直接用摘要作答）：**44,067 → 30,068 token（−31.8%）**。

## 4. 结论与使用建议

- 对"从大量日志里找结论/判断成败/提取错误"这类任务：压缩 2.0 收益明显（本次审计 67% 体积下降），且错误行 100% 保留，准确率无损；
- 对"必须逐行核对原文"的任务：模型可能主动恢复原文，省不下 Token，但也不会答错（恢复通道保证准确）；
- 默认仍为**观察模式**；确认要省 token 时再切"启用自动压缩"，随时可关；
- 不做的（按你的要求）：历史前缀重写、陈旧消息替换、会话裁剪、任何会改变既有上下文的操作。
